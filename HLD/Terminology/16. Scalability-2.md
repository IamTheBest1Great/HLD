## Scalability in High-Level Design (HLD)

Scalability ensures a system can handle increased load (traffic, data, or complexity) without redesigning the core architecture. In HLD, you plan for this upfront.

### Two Primary Dimensions of Scalability

| Dimension | Definition | When to Prioritize |
|-----------|------------|---------------------|
| **Vertical Scaling** (Scale Up) | Add more power to a single machine (CPU, RAM, storage) | Small to medium workloads, simpler apps, or when you have hard consistency requirements |
| **Horizontal Scaling** (Scale Out) | Add more machines/nodes to a pool | Large-scale systems, cloud-native apps, unpredictable traffic patterns |

---

## Specific Scalability Techniques & Their Scenarios

### 1. Load Balancing
**How it works:** Distributes incoming requests across multiple servers behind a single IP.

**When to use:**
- **Scenario A – Traffic spikes:** E-commerce during flash sales, ticket booking sites
- **Scenario B – Read-heavy workloads:** Social media feeds, news portals
- **Scenario C – Microservices:** Each service tier (API, web, etc.) needs distribution

**Methods:** Round-robin, least connections, IP hashing (sticky sessions), weighted distribution.

**Example:** Put an Application Load Balancer (ALB) in front of 10 stateless web servers. When traffic doubles, add 10 more servers.

### 2. Caching
**How it works:** Store frequently accessed data in fast, temporary storage (memory).

**When to use:**
- **Scenario A – Read-heavy with repetition:** User profiles, product catalogs, session data
- **Scenario B – Expensive computations:** ML inference results, aggregated reports
- **Scenario C – Database bottleneck:** When DB read latency > 10ms at scale

**Types & their use cases:**
| Cache Type | Best For | Example |
|------------|----------|---------|
| CDN (global) | Static assets (images, CSS, videos) | Netflix thumbnails |
| Application cache (Redis/Memcached) | Semi-dynamic data | Session tokens, user settings |
| Database query cache | Repeated identical queries | Lookup tables |

### 3. Database Scaling Strategies

#### a. Read Replicas
- **How:** Copy data to follower DBs; writes go to primary, reads go to replicas
- **When:** Read-heavy workload (80%+ reads), analytics queries that don't need real-time perfect consistency
- **Scenario:** Blog platform, reporting dashboards, product listing pages

#### b. Horizontal Partitioning (Sharding)
- **How:** Split data across multiple databases by a shard key (e.g., `user_id % 128`)
- **When:** Write-heavy workload, data too large for single machine (>1TB), need to isolate tenants
- **Scenario:** Messaging apps (chats by user ID), IoT data by device ID, SaaS multi-tenant systems

#### c. Vertical Partitioning
- **How:** Split tables into different databases (e.g., user profile vs. order history)
- **When:** Different access patterns per table, or to move infrequently used columns to cheaper storage
- **Scenario:** E-commerce where product metadata is read often, but inventory logs are written rarely

### 4. Asynchronous Processing & Message Queues
**How it works:** Decouple request receipt from processing using a queue (Kafka, RabbitMQ, SQS).

**When to use:**
- **Scenario A – Time-consuming operations:** Video encoding, email sending, PDF generation
- **Scenario B – Bursty traffic:** Order processing during checkout spikes (queue absorbs the burst)
- **Scenario C – Retry & fault tolerance:** Payment processing where external APIs may fail temporarily

**Example:** User uploads a video → API returns "processing" immediately → video transcoder workers pull from queue → user gets notification when done.

### 5. Microservices Architecture
**How it works:** Split a monolithic app into small, independently scalable services.

**When to use:**
- **Scenario A – Different scaling needs:** Payment service needs 50 instances; review service needs 5
- **Scenario B – Different teams own different features:** Allows independent deployment and scaling
- **Scenario C – Technology heterogeneity:** One service needs Python (ML), another needs Go (high concurrency)

**Trade-off:** Higher operational complexity (service discovery, distributed tracing, inter-service comms). Don't use for simple CRUD apps or early-stage startups.

### 6. Auto-scaling
**How it works:** Dynamically add/remove instances based on metrics (CPU, memory, request queue length).

**When to use:**
- **Scenario A – Predictable cyclical traffic:** Lunchtime food delivery apps, evening streaming spikes
- **Scenario B – Unpredictable viral traffic:** Product launches, social media trends
- **Scenario C – Cost optimization:** Dev/test environments that only run 9-5

**Metrics-based triggers:**
- CPU > 70% → scale out
- CPU < 30% → scale in
- Queue depth > 1000 messages → add more consumers

## Decision Framework: Which Method When?

| System Characteristic | Primary Scalability Method | Secondary |
|----------------------|---------------------------|-----------|
| Read-heavy, low write | Caching + Read replicas | CDN |
| Write-heavy (logs, IoT) | Sharding + Message queue | Vertical partitioning |
| Unpredictable traffic | Horizontal + Auto-scaling | Load balancing |
| Strong consistency required | Vertical (up to limit) + careful sharding | Avoid caching |
| Geographic distribution | CDN + Geo-DNS + Active-Active DBs | Edge computing |
| Low latency (<10ms) | Caching in-memory + Keep it small (vertical) | Predictable patterns |

---

## Common Anti-patterns to Avoid

1. **Premature sharding** – Adds complexity. Start with vertical scaling + read replicas first.
2. **Over-caching** – Stale data, cache invalidation complexity. Cache only what benefits from speed > freshness.
3. **Shared database across microservices** – Creates coupling. Each service should own its data store.
4. **Ignoring statelessness** – Sticky sessions kill horizontal scaling. Move state to client or distributed cache.

## 1. Vertical Scaling (Scale Up)

**Scenario:**  
- Small to medium workload where traffic grows slowly  
- Single-node databases that need strong ACID transactions  
- Legacy systems that cannot be refactored to distributed architecture  

**Example:**  
A startup’s internal CRM with 500 users. They move from 4 vCPU / 16 GB RAM to 32 vCPU / 128 GB RAM on the same server. Monthly growth is 5–10%, so they just upgrade hardware every year.

**When *not* to use:**  
- When you hit hardware limits (max 8 TB RAM on a single machine)  
- For global systems with unpredictable traffic spikes  

---

## 2. Horizontal Scaling (Scale Out)

**Scenario:**  
- Unpredictable or explosive traffic growth  
- Stateless services (web servers, APIs, image processors)  
- Cloud-native / microservices environments  

**Example:**  
**Twitter** during a major sports event. They have 100 stateless tweet-ingestion services behind a load balancer. Traffic jumps from 10k to 200k tweets/sec → auto-scaling spins up 500 more instances in 2 minutes.

**Real-world case:**  
Uber’s dispatch system – each city’s traffic pattern is different, so they horizontally scale per geographic shard.

---

## 3. Load Balancing (as a scalability enabler)

**Scenario:**  
- Distributing traffic across multiple servers to avoid overload  
- Zero-downtime deployments (rolling updates)  
- Handling asymmetric server capacity  

**Example:**  
**Amazon checkout page** – during Prime Day, they use weighted round-robin: new instances get lower weight until warmed up, then full weight. A Layer‑7 (HTTP) load balancer inspects session cookies to route requests to the same server only when needed (e.g., shopping cart).

---

## 4. Caching

### a. CDN (Content Delivery Network)

**Scenario:**  
- Serving static assets globally  
- Reducing origin server load for media-heavy sites  

**Example:**  
**Netflix** caches popular movie thumbnails and CSS/JS on CloudFront edge locations. When you open the app in Mumbai, the thumbnail is served from a nearby CDN node in India, not from AWS us-east-1. Cache hit rate >95%.

### b. In-Memory Cache (Redis / Memcached)

**Scenario:**  
- Repeated read queries with low write frequency  
- Session store for stateless apps  

**Example:**  
**GitHub** caches repository metadata (stars, forks, contributor list) in Redis. When thousands of users view the same popular repo (e.g., `torvalds/linux`), the database only gets hit once per cache TTL.

### c. Database Query Cache

**Scenario:**  
- Expensive aggregations or joins repeated often  
- Data changes rarely (e.g., reference tables)  

**Example:**  
**Airbnb** caches the result of “list all properties in Paris with average rating >4.5”. Instead of scanning 10k rows every second, they cache for 5 minutes.

---

## 5. Read Replicas

**Scenario:**  
- Application with >80% read operations  
- Analytics or reporting that can tolerate slight replication lag (seconds)  

**Example:**  
**Instagram feed** – each user’s home feed is a read query. The primary database handles writes (likes, comments, new posts). 15 read replicas serve all feed requests. If a replica lags by 2 seconds, you might not see your own post instantly – acceptable trade-off.

---

## 6. Database Sharding (Horizontal Partitioning)

**Scenario:**  
- Single database cannot handle write throughput  
- Data set too large for a single machine (>1 TB)  
- Need to isolate tenants (SaaS)  

**Example:**  
**Discord** shards message history by `guild_id` (server ID). Each shard holds messages for 100–200 servers. Write load is evenly distributed. When a new server is created, it's assigned to the shard with the lowest load.

**Another example:**  
**YouTube** comments sharded by `video_id`. Viral video comments go to a single shard – that’s fine because reads are high, but writes are also high. They further split that shard when it exceeds size.

**Sharding method used:**  
- **Hash sharding** – `hash(video_id) % N` → simple, even distribution.  
- **Range sharding** – `video_id` from 1M to 2M go to shard A. Good for time-series data.

---

## 7. Vertical Partitioning (different tables to different DBs)

**Scenario:**  
- Different tables have vastly different access patterns  
- Some columns are rarely used and can go to slower storage  

**Example:**  
**Etsy** moves `user_profile` (frequently read) to a high‑performance DB, and `user_login_history` (written once, rarely read) to a cheaper, slower DB. This reduces contention.

---

## 8. Asynchronous Processing with Message Queues

**Scenario:**  
- Request cannot be completed within <200 ms  
- Operation may fail and needs retry  
- Want to smooth out traffic bursts  

**Example:**  
**Stripe** payment processing:  
1. User clicks “Pay” → API returns `202 Accepted` immediately  
2. Payment job goes into RabbitMQ  
3. Worker processes: calls bank API, may retry 3 times  
4. Webhook notifies user when done  

**Another example:**  
**YouTube upload** – after upload, the video is pushed to a queue for transcoding, thumbnail generation, virus scanning. Each step can scale independently.

---

## 9. Auto-scaling

**Scenario:**  
- Traffic has peaks and valleys (e.g., 9 AM work start, lunchtime, evening entertainment)  
- Unpredictable viral spikes (product launch, celebrity tweet)  
- Cost optimization for dev/staging environments  

**Example:**  
**Slack** during work hours (9 AM–5 PM local time): minimum 50 instances. At 2 AM: scale down to 10 instances. They use predictive scaling based on historical patterns + CPU >70% threshold.

**Real‑world rule:**  
- **Reactive scaling** – when queue length > 1000 messages, add 10 consumers.  
- **Proactive scaling** – schedule 30 minutes before a known flash sale.

---

## 10. Microservices for Independent Scaling

**Scenario:**  
- Different features have completely different resource needs and traffic patterns  
- Teams want to deploy and scale independently  

**Example:**  
**Netflix** microservices:  
- **Playback service** – needs high network bandwidth and low latency → many small instances  
- **Recommendation service** – ML inference, needs GPU instances → scaled separately  
- **Billing service** – low traffic, runs on 2 tiny instances  

Without microservices, they’d have to over‑provision the entire monolith for the playback peak, wasting GPU resources.

## Decision Table – Scenario → Technique

| Scenario | Technique | Example Product |
|----------|-----------|----------------|
| Sudden traffic spike on a news site | Horizontal + auto‑scaling | CNN during election night |
| Users complain about slow product image loads | CDN + in‑memory cache | Shopify product pages |
| Database CPU at 100% due to reads | Read replicas + caching | Reddit front page |
| Database cannot keep up with writes (e.g., chat messages) | Sharding + message queue | WhatsApp message persistence |
| A single query runs for 5 seconds and is run 1000x/sec | Query result cache | Facebook friend suggestions |
| Need to process 1M video uploads per day, each takes 1 min | Async queue + worker pool | TikTok upload pipeline |
| Startup with 100 users, expects 200 next month | Vertical scaling | Small B2B SaaS |
| Global e‑commerce site with 10M products, search queries vary wildly | Sharding + CDN + replicas | Amazon product catalog |
