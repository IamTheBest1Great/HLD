## Durability in HLD

**Durability** is the guarantee that once a write operation (create, update, delete) is acknowledged as successful, the data will persist permanently — even in the face of power failures, crashes, network partitions, or disk corruption.

In distributed systems, durability is often formalized as part of the **ACID** properties (the “D” stands for Durability). It answers: *If the system crashes right now, will my data still be there when it restarts?*

### Core Principle: Redundant, Non‑volatile Storage + Write-Ahead Logging + Replication

---

## Durability Techniques & When to Use Them (with Examples)

### 1. Write-Ahead Logging (WAL)

**How it works:**  
Before modifying the main data store, the system writes the change to a sequential, append‑only log on persistent storage. If a crash happens, the system replays the log to recover unapplied changes.

**Scenario:**  
- Every database that guarantees durability (PostgreSQL, MySQL with InnoDB, SQLite)  
- Systems that need to recover quickly without data loss  
- Any system with random‑access mutable storage (B‑trees, LSM trees)

**Example:**  
**PostgreSQL** – WAL records every change. If the database crashes before flushing a data page to disk, on restart it reads the WAL and re‑applies the missing changes. Without WAL, a power loss could leave partially written pages or lost transactions.

**Another example:**  
**Kafka** – logs are written to disk sequentially (WAL essentially). Even if the broker crashes, messages up to the last flushed offset are durable.

---

### 2. Replication (Synchronous & Asynchronous)

#### a. Synchronous Replication

**How it works:**  
A write is considered durable only after it has been written to persistent storage on **two or more** nodes (primary + replica). If the primary crashes, the replica has the data.

**Scenario:**  
- Financial systems (payment processing, ledger)  
- Any system where zero data loss is mandatory  
- Single‑region high durability requirements

**Example:**  
**Google Spanner** – writes are synchronously replicated to at least two data centers. The commit returns only after both acknowledge persistence. If one data center loses power, no committed data is lost.

**Trade‑off:**  
Lower write throughput and higher latency (the write must wait for the slowest replica). May reduce availability if a replica is down (write would block).

#### b. Asynchronous Replication

**How it works:**  
The primary acknowledges the write as soon as it’s durable locally. Replicas catch up later. Some small window of data loss is possible (e.g., primary crashes before replicating).

**Scenario:**  
- Systems where a few seconds of data loss is acceptable (logs, metrics, social feeds)  
- High write throughput requirements  
- Cross‑region replication where latency is high

**Example:**  
**GitHub** – repository writes are durable on the primary region instantly, then asynchronously replicated to a secondary region. If the primary region explodes, you might lose the last 5 seconds of new pushes – acceptable for most developers (they can re‑push).

---

### 3. Distributed Consensus (Raft / Paxos)

**How it works:**  
A quorum of nodes must agree on the log entry before it is considered committed. Typically requires majority (N/2+1) nodes to acknowledge persistence.

**Scenario:**  
- Strongly consistent distributed databases (etcd, ZooKeeper, Consul)  
- Coordination services that cannot lose state  
- Systems requiring both durability and high availability under network partitions

**Example:**  
**etcd** (used by Kubernetes) – with 5 nodes, a write needs 3 acks to be durable. If 2 nodes fail, the cluster still works and data is safe. If 3 nodes fail (minority), the cluster stops accepting writes to prevent split‑brain and potential data loss.

**Another example:**  
**Kafka with `min.insync.replicas=2` and `acks=all`** – a message is durable only after the leader and at least one follower acknowledge the write. This is a variant of quorum.

---

### 4. Checksums & Data Integrity Verification

**How it works:**  
Each block of data is stored with a checksum (e.g., CRC32, SHA‑256). On every read, the system recomputes the checksum and compares. If mismatch → data corruption detected (bit rot, faulty hardware). The system can repair from another replica.

**Scenario:**  
- Any storage system where data can rot silently (all of them)  
- Long‑term archival storage  
- Systems that cannot afford silent corruption (medical records, legal documents)

**Example:**  
**ZFS** and **Btrfs** filesystems – checksum every block. When reading a file, ZFS verifies the checksum. If corrupted, it fetches the correct block from another disk (if mirrored/RAID).  
**S3** – stores ETags (MD5) and automatically scans for bit rot, repairing from redundant copies.

**Real‑world case:**  
**Facebook** once lost data from a corrupt RAID controller that wrote garbage silently. Checksums would have caught it. They now use checksums in their Haystack storage system.

---

### 5. Erasure Coding (instead of full replication)

**How it works:**  
Data is split into `k` fragments, encoded into `n` fragments (n > k). Any `k` of the `n` fragments can reconstruct the original. Storage overhead = n/k (e.g., 1.5x vs. 3x for triple replication).

**Scenario:**  
- Large‑scale blob storage (videos, backups, cold storage)  
- When storage cost is more important than read performance  
- Durable archival (tolerating multiple failures)

**Example:**  
**HDFS** (Hadoop) with erasure coding – stores 1.5x overhead instead of 3x replication. Can tolerate any 2 failures out of 6 fragments.  
**Backblaze B2** – uses 17+3 erasure coding (17 data fragments + 3 parity) across 20 drives. Any 17 fragments reconstruct the file. They achieve 99.999999% durability at much lower cost than replication.

**When to use vs. replication:**  
- **Replication** – better for hot data, random reads, small objects (lower CPU overhead)  
- **Erasure coding** – better for cold data, large sequential reads, cost‑sensitive scenarios

---

### 6. Durable Commit Logs (Message Queues / Event Sourcing)

**How it works:**  
Instead of overwriting state, all changes are appended to an immutable log on disk. The current state is derived by replaying the log. The log itself is replicated and checksummed.

**Scenario:**  
- Event‑sourced systems  
- Message brokers that guarantee at‑least‑once delivery  
- Systems that need point‑in‑time recovery

**Example:**  
**Kafka** – each partition is an append‑only log on disk. Messages are durable once flushed (controlled by `flush.ms` or `flush.messages`). Even if all brokers crash, the log survives and can be replayed.  
**EventStoreDB** – stores events in a durable log. The read model is rebuilt by replaying events. No data is ever overwritten.

---

### 7. Non‑Volatile Memory (NVDIMM) / Battery‑Backed RAM

**How it works:**  
Special hardware that acts like RAM but retains data across power cycles. Used as a super‑fast write cache that is automatically flushed to persistent storage.

**Scenario:**  
- Systems requiring sub‑millisecond write latency with full durability  
- High‑frequency trading, real‑time bidding  
- Databases that need to avoid the latency of disk fsync

**Example:**  
**Oracle Exadata** – uses battery‑backed write cache. A write is acknowledged as soon as it hits the cache. If power fails, the battery preserves the cache until power returns and the cache is flushed to disk. This gives disk‑level durability with memory speed.

**Trade‑off:**  
Expensive, special hardware. Not used in most cloud applications.

---

### 8. RAID (Redundant Array of Independent Disks)

**How it works:**  
Multiple physical disks appear as one logical volume. Different levels provide different durability/performance trade‑offs.

**Scenario:**  
- On‑premise databases, file servers  
- Protection against single‑disk failure (but not against controller or software bugs)  
- Cheaper than distributed replication for local durability

**Example:**  
**RAID 10** (mirroring + striping) – each block is written to two disks. If one disk dies, data is still available. Used in many on‑prem MySQL deployments.  
**RAID 6** – two parity disks; can tolerate any two disk failures. Good for large capacity drives where rebuild time is long.

**Note:** RAID is not enough for full durability – it doesn’t protect against fire, theft, or software corruption. Always combine with remote replication.

---

### 9. Backup & Point‑in‑Time Recovery (PITR)

**How it works:**  
Periodically take full snapshots + store continuous WAL logs. Allows restoring to any point in time (e.g., 5 seconds before a user accidentally ran `DELETE * FROM users`).

**Scenario:**  
- Every production database that stores critical data  
- Compliance requirements (financial, medical)  
- Protection against human error (not just hardware failure)

**Example:**  
**AWS RDS** – automated daily snapshots + transaction logs (for PITR). You can restore to any second in the last 35 days. If a developer drops a table, you restore a new DB instance to the moment just before the drop.

**Another example:**  
**Git** – every commit is a durable backup. You can revert to any previous state. Not a classic DB, but a great example of point‑in‑time recovery.

---

### 10. Immutable Infrastructure & Object Versioning

**How it works:**  
Never overwrite or delete the previous version of an object. Each write creates a new version. Deletion only marks the object as deleted (soft delete) for a retention period.

**Scenario:**  
- Cloud storage buckets with critical assets  
- Protecting against accidental overwrites or ransomware  
- Compliance with data retention laws

**Example:**  
**S3 Versioning** – enable bucket versioning. If someone overwrites a file, the old version remains. If someone deletes a file, a delete marker is added but the file can be restored. You can set lifecycle rules to delete old versions after 90 days.

**Real‑world case:**  
**Wayback Machine (Internet Archive)** – stores every version of every web page ever crawled. Extreme durability through immutability.

## Decision Table – Scenario → Durability Technique

| Scenario | Primary Technique | Secondary |
|----------|------------------|-----------|
| Bank account balance – cannot lose any committed transaction | Synchronous replication + WAL + quorum | Backup + PITR |
| User uploaded profile picture – okay to lose if upload fails but not after success | WAL + asynchronous replication | Object versioning |
| 1TB database on a single server | RAID 10 + WAL + daily backups to remote storage | Replication to standby |
| Global video storage (YouTube) – petabytes, low cost required | Erasure coding + checksums + multi‑region async replication | Immutable object versions |
| Microservice that processes payments | Durable commit log (Kafka) with `acks=all` and `min.insync.replicas=2` | Idempotent consumer |
| Logging system – losing 0.1% of logs is fine | Asynchronous replication + WAL | No synchronous acks |
| Kubernetes cluster state (etcd) | Distributed consensus (Raft) with 5 nodes | Periodic snapshots |
| Legal document storage (cannot be tampered) | Checksums + immutable versioning + write‑once media | Cryptographic signatures |
| High‑frequency trading – sub‑ms latency with durability | NVDIMM battery‑backed cache + synchronous replication to 2 nodes | Custom FPGA logic |
| User accidentally deletes entire project folder | Point‑in‑time recovery (snapshots + WAL) + soft delete (trash folder) | Versioning |

## Common Anti‑patterns for Durability

1. **Relying on RAID only** – Doesn’t protect against fire, ransomware, or `rm -rf`. Always have off‑site backups.
2. **Disabling fsync for “performance”** – Many databases let you disable durable commits. Only do this for test environments or when you truly accept data loss.
3. **Single region / single AZ** – A power outage or network partition can make all replicas unreachable. Use multi‑AZ at minimum.
4. **Not verifying backups** – Backup is not durable until you’ve successfully restored from it. Test restores regularly.
5. **Asynchronous replication without monitoring** – If the replica falls far behind, a primary crash loses more data. Monitor replication lag.
6. **No checksums** – Silent corruption can go unnoticed for years. Always enable checksums on storage systems.

## Summary for HLD Interviews – Durability

> *“To ensure durability, I start with **write‑ahead logging (WAL)** so no committed change is lost on crash. I use **synchronous replication** to at least two nodes for critical data that cannot tolerate any loss, and **asynchronous replication** for cross‑region backups. I add **checksums** to detect silent corruption, and **regular backups with point‑in‑time recovery** to guard against human error. For large‑scale blob storage, I use **erasure coding** to reduce overhead while maintaining high durability. I also enable **object versioning** where applicable to prevent accidental overwrites. Finally, I verify that every ‘durable’ write is acknowledged only after it’s on at least two physically independent persistent media.”*
