## Fault Tolerance in HLD

**Fault tolerance** is the ability of a system to continue operating correctly (though possibly at reduced performance) when one or more of its components fail. It goes beyond high availability: fault tolerance implies **no interruption** from the user’s perspective, whereas high availability might tolerate a few seconds of downtime during failover.

**Key distinction:**
- **High Availability (HA)** – minimize downtime (e.g., 99.99% uptime, but a 5‑second failover is acceptable)
- **Fault Tolerance (FT)** – zero perceived downtime; the failure is masked completely

### Core Principles: Redundancy + Isolation + Failure Masking + Automatic Recovery

## Fault Tolerance Techniques & When to Use Them (with Examples)

### 1. Redundancy with Active‑Active (No Failover Delay)

**How it works:** Multiple instances all handle traffic simultaneously. If one fails, the others continue without any interruption. No leader election, no failover time.

**Scenario:**  
- Stateless services where any instance can handle any request  
- Systems that cannot tolerate even a second of downtime  
- High‑throughput, low‑latency requirements

**Example:**  
**Google Search frontend** – thousands of web servers behind a load balancer. If one server crashes, the load balancer stops sending traffic to it within milliseconds. Users see no error, no delay.  
**Cloudflare DNS** – anycast network; if one data center goes offline, BGP routing shifts traffic to the next closest in <1 second.

**When to avoid:**  
- Stateful services (unless you have distributed state like CRDTs)  
- When you need strong consistency across all nodes (leaderless is complex)

---

### 2. Replication with Leader Election (Active‑Passive with Fast Failover)

**How it works:** One active node handles requests; one or more standbys replicate state. On failure, the standby becomes active. Failover time can be milliseconds if using consensus.

**Scenario:**  
- Stateful services (databases, message queues)  
- When you can tolerate <1 second failover (fault‑tolerant enough for most)  
- Systems requiring strong consistency

**Example:**  
**etcd** (Raft consensus) – 3‑node cluster. Leader fails → followers elect a new leader in ~100‑300ms. Clients automatically retry and connect to the new leader. No data loss.  
**PostgreSQL with Patroni** – uses etcd or ZooKeeper for leader election. Failover in 2‑5 seconds (not quite zero downtime, but high availability). For true fault tolerance, use synchronous replication + fast failover.

---

### 3. Checkpointing & State Machine Replication

**How it works:** The system’s state is periodically snapshotted (checkpoint). On failure, the system restores from the latest checkpoint and replays operations from a log. Used in stream processing and long‑running computations.

**Scenario:**  
- Stream processors (Flink, Spark Streaming)  
- Long‑running batch jobs that cannot restart from scratch  
- Systems that need exactly‑once processing semantics

**Example:**  
**Apache Flink** – checkpoints state to distributed storage (S3, HDFS) every few seconds. If a task manager fails, the job restarts from the last checkpoint and replays the subsequent stream. End users see a brief pause (seconds), but processing continues correctly.  
**Microsoft Excel** – auto‑recovery saves a checkpoint every 10 minutes. Crash → reopen with most of your work.

---

### 4. Retry & Idempotency (Client‑Side Fault Tolerance)

**How it works:** The client automatically retries failed requests. Idempotency ensures retries don’t cause duplicate side effects.

**Scenario:**  
- Transient network failures, timeouts, or temporary overloads  
- Any distributed system where failures are expected (cloud, microservices)  
- When the server can be made idempotent

**Example:**  
**AWS SDK** – built‑in retry with exponential backoff (e.g., 3 retries). If DynamoDB returns a `ProvisionedThroughputExceededException`, the SDK retries after a delay.  
**Stripe API** – client sends an idempotency key. If the first request times out, the client retries with the same key; Stripe returns the same response without charging twice.

**When not enough:**  
- Server is permanently down (retries won’t help)  
- Stateful operations that cannot be made idempotent

---

### 5. Bulkheading (Resource Isolation)

**How it works:** Partition the system into isolated pools (threads, connections, CPU, memory) so that a failure in one component doesn’t exhaust resources for others.

**Scenario:**  
- Multi‑tenant systems (one noisy tenant can’t crash others)  
- Microservices where a downstream failure could cause cascading failures  
- Any system where you must guarantee “failure containment”

**Example:**  
**Netflix Hystrix (or Resilience4j)** – each downstream dependency gets its own thread pool. If the “recommendations” service slows down, only its thread pool fills up; the “playback” service remains unaffected.  
**Kubernetes resource limits** – each pod has CPU/memory limits. A memory leak in one pod causes that pod to be OOM‑killed, not the entire node.

**Real‑world:**  
**Airbnb** – isolates search, booking, and payment services into separate thread pools. A search spike doesn’t block bookings.

---

### 6. Circuit Breaker (Preventing Cascading Failures)

**How it works:** Monitors failures to a dependency. When failure rate exceeds a threshold, the circuit “opens” – requests fail immediately without calling the dependency, giving it time to recover.

**Scenario:**  
- Preventing a slow or failing downstream service from taking down the caller  
- Systems that can degrade gracefully (show stale data or a fallback)  
- Microservices with many dependencies

**Example:**  
**Netflix** – if the “movie metadata” service starts timing out, the circuit breaker opens. The UI shows “Recommendations unavailable” instead of hanging. After 30 seconds, the breaker allows one test request; if successful, the circuit closes.  
**Payment gateway** – if the external credit card processor fails, the circuit breaker opens and the system falls back to “try again later” instead of exhausting all threads.

**When to use:**  
- When you have fallback logic (cache, default value, error message)  
- When the dependency is external and you cannot control its reliability

---

### 7. Watchdog & Health Checks

**How it works:** A separate process monitors the health of components. If a component becomes unresponsive or returns errors, the watchdog restarts it, fails over, or alerts.

**Scenario:**  
- Every production system (basic fault detection)  
- Systems that can self‑heal by restarting failed processes  
- Containerized environments (Kubernetes)

**Example:**  
**Kubernetes liveness probe** – kubelet periodically pings `GET /health`. If the probe fails 3 times, Kubernetes restarts the container. This fixes deadlocks, memory leaks, or crashes.  
**Systemd** – can restart a failed service automatically (e.g., `Restart=on-failure`).

---

### 8. Replication with Quorum (Tolerating Byzantine Failures – Advanced)

**How it works:** Use N replicas (e.g., 3, 5, 7) and require quorum (W+R>N). Can tolerate up to `(N-1)/2` failures. For **Byzantine** (malicious) failures, use Byzantine Fault Tolerance (BFT) with N>=3f+1.

**Scenario:**  
- Mission‑critical systems where failures can be arbitrary (corruption, malicious)  
- Blockchain, flight control, nuclear reactors  
- Systems with untrusted nodes

**Example:**  
**Practical Byzantine Fault Tolerance (PBFT)** – used in some blockchains (Hyperledger Fabric). With 4 nodes, can tolerate 1 Byzantine failure.  
**AWS KMS** – uses quorum of hardware security modules (HSMs). If one HSM gives a corrupted signature, the quorum rejects it.

**Most systems don’t need BFT** – crash‑fault tolerance (Raft) is sufficient for 99% of use cases.

---

### 9. Redundant Hardware (Physical Fault Tolerance)

**How it works:** Duplicate power supplies, network interfaces, disks, memory (ECC), CPUs. The system continues even if one hardware component fails.

**Scenario:**  
- On‑premise servers (data centers)  
- Mission‑critical appliances (medical, industrial)  
- When software redundancy isn’t enough (e.g., single server must be fault‑tolerant)

**Example:**  
**RAID 1/10** – mirrored disks. One disk fails; the system continues using the other.  
**ECC RAM** – detects and corrects single‑bit memory errors. Prevents silent data corruption.  
**Dual power supplies** – one fails; the server keeps running.

---

### 10. Graceful Degradation (Fault Tolerance at the Feature Level)

**How it works:** When a component fails, the system disables only the affected features but keeps core functionality running.

**Scenario:**  
- Feature‑rich applications where some features are non‑critical  
- Systems that must stay up at all costs (emergency services, e‑commerce)  
- When you have fallback defaults

**Example:**  
**Amazon product page** – if the “customer reviews” service fails, the page loads without reviews. The “Add to Cart” button still works.  
**Maps app** – if real‑time traffic data fails, the app falls back to showing estimated travel time without live traffic.

---

### 11. Redundant Request Execution (Hedged Requests)

**How it works:** Send the same request to multiple replicas and take the first response. Cancel the others. Used to tolerate slow or failed nodes.

**Scenario:**  
- Very low‑latency requirements (sub‑millisecond)  
- Systems with variable tail latency (long‑tail latency problem)  
- When you have spare capacity

**Example:**  
**Google Search** – sends the same query to two backends. The first response wins. This reduces the 99th percentile latency from 200ms to 50ms.  
**Cassandra** – speculative retry. If the first replica doesn’t respond within 10ms, a second request is sent to another replica.

---

### 12. Compensating Actions (for Transactional Fault Tolerance)

**How it works:** In long‑running transactions (sagas), if a step fails, the system runs a compensating action to undo previous steps. This provides fault tolerance without distributed transactions.

**Scenario:**  
- Microservices where you cannot use 2PC (two‑phase commit)  
- Long‑running business processes (travel booking, order fulfillment)  
- When you need to maintain consistency despite failures

**Example:**  
**Travel booking saga** – steps: book flight → book hotel → charge credit card. If charging fails, the saga runs compensating actions: cancel hotel → cancel flight. The user sees a “booking failed” message, but no inconsistent state.

## Decision Table – Scenario → Fault Tolerance Technique

| Scenario | Primary Technique | Secondary |
|----------|-------------------|-----------|
| Stateless web server (e.g., API gateway) | Active‑active redundancy + load balancer health checks | Auto‑scaling to replace failed instances |
| Database (stateful) with zero downtime requirement | Leader election + synchronous replication (Raft) | Read replicas for query offloading |
| Stream processing job that cannot lose state | Checkpointing + state machine replication | Exactly‑once semantics (Flink) |
| Microservice calling an unreliable external API | Circuit breaker + retry with backoff + fallback | Bulkheading (separate thread pool) |
| Multi‑tenant SaaS – noisy neighbor problem | Bulkheading (resource isolation per tenant) | Rate limiting per tenant |
| Real‑time bidding (low latency, variable tail) | Hedged requests (send to two replicas) | Timeout + retry to different replica |
| Long‑running business transaction (e.g., order + payment + shipping) | Saga pattern with compensating actions | Idempotency keys for each step |
| Single server that must survive hardware failure | Redundant hardware (ECC RAM, RAID, dual PSU) | Watchdog for process restart |
| System that must survive malicious/corrupt nodes (blockchain) | Byzantine fault tolerance (PBFT, HotStuff) | Quorum with N>=3f+1 |
| Feature‑rich website where some features are optional | Graceful degradation + feature toggles | Circuit breaker for each feature |

## Common Anti‑patterns for Fault Tolerance

1. **No health checks** – Load balancer keeps sending traffic to dead servers → user errors.
2. **Infinite retries without backoff** – Can overwhelm a struggling service (use exponential backoff + max retries).
3. **Shared thread pools across dependencies** – One slow dependency can exhaust all threads (use bulkheading).
4. **No circuit breakers** – A failing downstream service causes cascading failures across the system.
5. **Assuming failover is instantaneous** – Test failover regularly; network partitions, DNS propagation, and connection pools add delays.
6. **Not testing fault injection** – Chaos engineering (Netflix Chaos Monkey) reveals hidden fault tolerance gaps.
7. **Single region deployment** – A regional power outage takes down everything (use multi‑region for critical systems).
