## Reliability in HLD

**Reliability** is the probability that a system will function without failure for a specified period of time under given conditions. It answers: *How long can the system run before something breaks?* Reliability is often measured as **Mean Time Between Failures (MTBF)** and **Mean Time To Repair (MTTR)**.

**Key distinction from other pillars:**
- **Availability** = uptime percentage (MTBF / (MTBF + MTTR))
- **Fault Tolerance** = ability to continue operating during failures
- **Reliability** = the *duration* of error‑free operation (often about reducing failure rates, not just masking them)

In HLD, reliability is ensured by:
- **Eliminating single points of failure** (already covered in FT/HA)
- **Reducing component failure rates** (using reliable hardware, quality code, redundancy)
- **Detecting and recovering from failures quickly** (minimizing MTTR)
- **Designing for predictable degradation** (no cascading failures)

### Core Principles: Redundancy + Failure Detection + Fast Recovery + Quality Assurance

## Reliability Techniques & When to Use Them (with Examples)

### 1. Redundant Components (N+1, 2N, etc.)

**How it works:** Add extra components beyond the minimum required. If one fails, the others continue.

**Scenario:**  
- Critical infrastructure (power supplies, network links, cooling)  
- Systems that cannot tolerate any downtime  
- When component MTBF is known and you need to achieve a system MTBF target

**Example:**  
**Data center power** – N+1 redundant generators and UPS units. One generator fails; the others still supply power.  
**Airplane avionics** – triple‑redundant flight computers (voting). If one gives a different output, the other two overrule it.

**When to use:**  
- When the cost of failure is extremely high (safety, finance)  
- When component reliability is low but you need high system reliability

---

### 2. Mean Time Between Failures (MTBF) Design – Use High‑Reliability Components

**How it works:** Choose components (hardware, software libraries, services) with proven high MTBF. Use enterprise‑grade rather than consumer‑grade.

**Scenario:**  
- Long‑lifetime systems (spacecraft, industrial controllers)  
- Systems that are hard to repair (remote sensors, undersea cables)  
- When you cannot afford frequent failures (even with redundancy)

**Example:**  
**Mars rover** – uses radiation‑hardened CPUs with MTBF of decades. Consumer CPUs would fail in weeks due to cosmic rays.  
**Google’s custom servers** – they use lower‑reliability components but compensate with software redundancy. That’s a trade‑off: low component reliability but high system reliability via redundancy.

**When to avoid:**  
- When software redundancy is cheaper than high‑reliability hardware (most cloud apps)

---

### 3. Failure Detection & Heartbeats

**How it works:** Components send periodic “I’m alive” signals. If a heartbeat is missed, the system assumes failure and initiates recovery.

**Scenario:**  
- Distributed systems (leader election, cluster management)  
- Monitoring systems (Nagios, Prometheus)  
- Any system that needs to detect failures autonomously

**Example:**  
**Hadoop NameNode** – DataNodes send heartbeats every 3 seconds. If a DataNode misses 10 heartbeats, NameNode marks it dead and replicates its blocks elsewhere.  
**Kubernetes** – kubelet sends heartbeats to the control plane. If a node stops sending, pods are rescheduled.

**Trade‑off:**  
- Short heartbeat interval → faster detection, higher overhead  
- Long interval → slower detection, lower overhead

---

### 4. Timeouts & Retries with Bounded Backoff

**How it works:** Set a timeout for each operation. If it expires, assume failure and retry (with backoff) up to a limit.

**Scenario:**  
- Unreliable networks (cloud, mobile)  
- External API calls  
- Any operation that may hang indefinitely

**Example:**  
**AWS SDK** – default timeout 3 seconds for API calls. If timeout, retry up to 3 times with exponential backoff (100ms, 200ms, 400ms). This masks transient failures, improving reliability.

**When to tune:**  
- Too short → false failures (slow network)  
- Too long → resource waste (threads stuck)

---

### 5. Redundant Requests (Hedged Requests) – also for reliability

**How it works:** Send the same request to multiple backends; take the first response. This improves reliability against slow or tail‑latency failures.

**Scenario:**  
- Systems where latency is critical and you can afford extra capacity  
- When you have many replicas and variable performance  

**Example:**  
**Google Search** – sends query to two backends. The first response wins. This reduces the chance that a single slow node delays the user.

**Reliability benefit:** Masks “gray failures” (node is alive but slow or intermittently faulty).

---

### 6. Monitoring & Alerting (Proactive Reliability)

**How it works:** Continuously collect metrics (error rates, latency, resource usage). Set alerts when metrics deviate from normal. Detect issues before they cause user‑visible failures.

**Scenario:**  
- Every production system  
- When you need to meet SLOs (Service Level Objectives)  
- To reduce MTTR by catching failures early

**Example:**  
**Prometheus + Grafana** – monitor error rate on API endpoints. If error rate exceeds 1% for 2 minutes, page the on‑call engineer. The issue is fixed before it becomes a full outage.  
**New Relic** – alerts when database connection pool is 90% full, allowing proactive scaling.

---

### 7. Chaos Engineering (Testing Reliability)

**How it works:** Intentionally inject failures (kill servers, corrupt packets, exhaust memory) in production or staging to verify that the system remains reliable.

**Scenario:**  
- Large‑scale distributed systems (Netflix, Amazon)  
- Systems that claim high reliability – you must prove it  
- Before major events (Black Friday, elections)

**Example:**  
**Netflix Chaos Monkey** – randomly terminates EC2 instances during business hours. Services must survive without user impact. If they don’t, engineers fix the gaps. This continuously improves reliability.

**Another example:**  
**AWS Fault Injection Simulator** – test how your application handles API throttling, latency spikes, or instance termination.

---

### 8. Graceful Degradation (Reliability through reduced functionality)

**How it works:** When a component fails, the system continues with reduced features rather than crashing entirely.

**Scenario:**  
- Systems with many optional features  
- When you cannot guarantee all features will always work  
- To maintain core reliability at the expense of non‑critical functions

**Example:**  
**Spotify** – if the “recommendations” service fails, the app still plays music (core function). The “Discover Weekly” playlist may be empty, but the user can still listen.  
**Tesla autopilot** – if a camera fails, the system disables lane keeping but still provides adaptive cruise control.

---

### 9. Retry Storm Prevention (Jitter & Circuit Breaker)

**How it works:** When many clients retry simultaneously after a failure, they can create a “retry storm” that overloads the recovering service. Add jitter to retry delays and use circuit breakers.

**Scenario:**  
- Large‑scale systems with many clients  
- After a brief outage, many requests come back at once  

**Example:**  
**Twitter** – after a transient database glitch, thousands of clients retry at exactly the same time, causing a second spike. They add randomized jitter (±20% of delay) and exponential backoff to spread out retries.  
**Circuit breaker** – after 50% failure rate, open circuit; clients fail fast, giving the service time to recover.

---

### 10. Redundant Data Paths (Network Reliability)

**How it works:** Use multiple network links (different cables, different ISPs, BGP anycast). If one path fails, traffic reroutes automatically.

**Scenario:**  
- Data centers with critical connectivity  
- CDNs and DNS providers  
- Financial trading networks

**Example:**  
**Cloudflare** – uses BGP anycast across 300+ cities. If one data center loses connectivity, routes are withdrawn and traffic flows to the next closest.  
**Google’s B4 network** – redundant fiber paths between data centers; software‑defined networking reroutes within milliseconds.

---

### 11. Statelessness (for higher reliability of individual components)

**How it works:** Make services stateless so that any instance can handle any request. Failure of one instance has no lasting impact; clients simply retry to another instance.

**Scenario:**  
- Web servers, APIs, image processors  
- Any service that doesn’t need to remember past requests  
- When you want to replace failed instances without state recovery

**Example:**  
**Cloud‑native applications** – store session state in Redis (external cache) rather than in‑memory. If a web server dies, another server picks up the session from Redis. This makes individual server failures invisible to users.

**Reliability benefit:** MTTR is near zero – just kill and restart.

---

### 12. Idempotent Operations

**How it works:** Design operations so that executing them multiple times has the same effect as executing once. This allows safe retries, improving reliability in the face of network failures.

**Scenario:**  
- Payment processing, order creation, data updates  
- Any operation that may be retried due to timeouts  

**Example:**  
**Stripe** – idempotency key ensures that retrying a charge request does not double‑charge. The first request processes the payment; subsequent identical requests return the same result. This masks transient failures without side effects.

## Reliability Metrics to Design For (in HLD)

| Metric | Definition | Target Example |
|--------|------------|----------------|
| **MTBF** (Mean Time Between Failures) | Average time between failures | 1 year for a critical service |
| **MTTR** (Mean Time To Repair) | Average time to detect + recover | 5 minutes (automated) |

| **SLO** (Service Level Objective) | Internal reliability target | 99.95% successful requests per month |
| **SLA** (Service Level Agreement) | External guarantee | 99.9% uptime, with credits for breach |

## Common Anti‑patterns for Reliability

1. **No retries** – Transient failures cause user errors (add retries with backoff).
2. **Retries without idempotency** – Duplicate side effects (use idempotency keys).
3. **No circuit breakers** – A slow dependency can hang the whole system.
4. **No monitoring** – You don’t know you’re failing until users complain.
5. **Testing only with happy path** – Reliability requires testing failure scenarios (chaos).
6. **Single region** – A natural disaster or network cut takes everything down.
7. **Long timeouts** – A stuck request ties up resources for too long (use short timeouts + retry).
8. **No graceful degradation** – A minor feature failure brings down the whole app.
