## Consistency Techniques: When to Use What (by Application Type & Situation)

Below is a **decision guide** that maps real-world application needs and situations to the right consistency technique.

| If your application… | Then you need… | Use this technique | Why |
|---------------------|----------------|--------------------|-----|
| **Handles money transfers, inventory reservations, or any operation that must be atomic** | Strong consistency (linearizability) | **Distributed transactions (2PC) or leader‑based with SERIALIZABLE isolation** | A partial update (e.g., debit without credit) breaks business rules. |
| **Lets users update their profile and then immediately view it** | Read‑your‑writes | **Leader reads for user’s own data; followers for others** | The user expects to see their change right away. Others can wait. |
| **Has a shopping cart where items must never be lost or double‑counted** | Strong consistency for cart updates | **Idempotency keys + conditional writes** | Prevents duplicate adds on retry; ensures cart total is accurate. |
| **Shows a “like” count on a post – it’s okay if it’s slightly off for a few seconds** | Eventual consistency | **Quorum with W=1, R=1 + read‑repair** | High write throughput; small temporary inconsistency is acceptable. |
| **Is a collaborative editor (Google Docs, Figma)** | Strong eventual consistency (no conflicts) | **CRDTs or Operational Transforms (OT)** | Multiple users edit same document; merges must be automatic and deterministic. |
| **Runs a leader election for a critical background job (e.g., scheduler)** | Linearizable (only one leader) | **Distributed consensus (Raft, Paxos)** | Two active leaders would corrupt state. |
| **Has a DNS or CDN – changes are rare and can take hours to propagate** | Eventual consistency | **Caching with TTL + monotonic reads** | Performance and scalability matter more than immediate freshness. |
| **Processes payments or orders – retries are common (network timeouts)** | Exactly‑once semantics | **Idempotency keys** | Prevents duplicate charges or orders when clients retry. |
| **Maintains a distributed counter (e.g., page views, votes)** | Eventual consistency, but no lost increments | **CRDT counter (G‑Counter) or quorum with read‑repair** | Last‑write‑wins would drop increments. CRDTs merge correctly. |
| **Needs to enforce a unique constraint (e.g., username, email) across a cluster** | Strong consistency on check‑and‑set | **Leader‑based check + atomic compare‑and‑set** | Without it, two users could register the same username. |
| **Has a microservices architecture with a saga (e.g., travel booking)** | No global strong consistency; per‑service local consistency | **Saga pattern with compensating transactions** | Distributed transactions are too slow and fragile across services. |
| **Is a real‑time leaderboard (game scores)** | Sequential consistency per player, but global eventual | **Single leader (Redis sorted set) or CRDT leaderboard** | Simpler to use a single node; CRDTs for multi‑region. |
| **Runs analytics queries on a replica** | Stale reads are fine (seconds old) | **Asynchronous replication + read replica** | Offloads leader, improves scalability. |
| **Must survive a network partition but still accept writes (e.g., mobile app offline)** | Availability over consistency | **Multi‑leader or leaderless + conflict resolution (LWW or custom)** | AP systems (Cassandra, DynamoDB) allow writes during partition. |
| **Has a global user session store – users must stay logged in across requests** | Monotonic reads (never see an older session after a newer one) | **Sticky sessions or distributed cache with monotonic read guarantee** | Prevents “I was logged in, now I’m not” glitches. |

## Decision Flowchart (Mental Model)

```
Start: Does your operation need to be atomic (all or nothing)?
  ├─ YES → Use distributed transaction (2PC) or Saga (if across microservices)
  └─ NO  → Continue

Does a user need to see their own write immediately?
  ├─ YES → Use leader reads for that user’s data
  └─ NO  → Continue

Can you tolerate temporary inconsistency (seconds to minutes)?
  ├─ YES → Use eventual consistency (quorum W=1,R=1 + read‑repair)
  └─ NO  → Use strong consistency (quorum W+R>N or leader reads)

Is the system multi‑leader or leaderless (e.g., multi‑region)?
  ├─ YES → Must handle conflicts → Use CRDTs, vector clocks, or LWW
  └─ NO  → Single leader replication is simpler

Does the operation need to be idempotent (safe to retry)?
  ├─ YES → Add idempotency keys
  └─ NO  → Ensure no duplicate side effects
```

## Summary Table: Each Technique’s “When” & “Example Application”

| Technique | When to use | Example application |
|-----------|-------------|----------------------|
| **Leader‑based replication** | Most applications that can tolerate a single write master | Traditional web app (Rails + PostgreSQL) |
| **Quorum (W+R>N)** | You need tunable consistency; can trade off availability | Cassandra (banking backend for read‑heavy) |
| **Distributed consensus (Raft)** | You need linearizable writes and leader election | etcd (Kubernetes control plane) |
| **Idempotency keys** | Any API that may be retried and has side effects | Stripe payments, order submission |
| **CRDTs** | Collaborative, offline‑first, or high‑conflict environments | Apple Notes, Redis Enterprise |
| **Read‑repair + hinted handoff** | Eventually consistent systems that converge quickly | Cassandra, DynamoDB |
| **Distributed transactions (2PC)** | When you must have ACID across multiple databases (rare) | Legacy financial systems |
| **Saga pattern** | Microservices where 2PC is too heavy | Travel booking (hotel + flight + car) |
| **Sticky sessions** | When you need monotonic reads without distributed cache | Legacy session management |
| **TTL + caching** | When staleness is acceptable (e.g., DNS, product catalog) | Memcached, CDN, DNS |
