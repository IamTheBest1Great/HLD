## Security in HLD

**Security** in HLD means designing a system to protect data confidentiality, integrity, and availability (the CIA triad) against unauthorized access, tampering, disclosure, or denial-of-service attacks. It’s not just a feature – it’s a cross‑cutting concern that must be baked into every layer: network, application, data, and operations.

### Core Principles: Defense in Depth, Least Privilege, Zero Trust, Secure by Default

---

## Security Techniques & When to Use Them (with Examples)

### 1. Authentication (AuthN)

**How it works:** Verifying the identity of a user, service, or device. “Who are you?”

**Common methods:**
- **Password + MFA** (most common)
- **OAuth2 / OpenID Connect** (social login, enterprise SSO)
- **API keys** (machine‑to‑machine)
- **mTLS** (service‑to‑service)
- **Biometrics** (fingerprint, face)

**Scenario & Example:**

| Scenario | Technique | Example |
|----------|-----------|---------|
| User logging into a banking app | Password + MFA (TOTP or SMS) | Chase Bank – after password, asks for 6‑digit code from authenticator app |
| Microservice calling another internal service | mTLS (mutual TLS) with SPIFFE identity | Kubernetes service mesh (Istio) – each pod gets a certificate; only authenticated services can talk |
| Third‑party app accessing your Google Calendar | OAuth2 delegation | “Sign in with Google” – user grants scoped access without sharing password |
| CI/CD pipeline pushing a Docker image to registry | API key + IP whitelist | GitHub Actions uses a secret API key to authenticate to AWS ECR |

---

### 2. Authorization (AuthZ)

**How it works:** Determining what an authenticated identity is allowed to do. “What can you do?”

**Common models:**
- **RBAC** (Role‑Based Access Control) – assign roles to users, permissions to roles
- **ABAC** (Attribute‑Based Access Control) – dynamic rules based on user attributes, resource attributes, environment
- **ReBAC** (Relationship‑Based Access Control) – permissions derived from relationships (e.g., “owner of this document”)
- **ACL** (Access Control Lists) – per‑resource list of who can do what

**Scenario & Example:**

| Scenario | Model | Example |
|----------|-------|---------|
| Employee HR portal – managers can see their team’s salaries, employees see only their own | RBAC | `role=manager` → can read `salary` for users in `department=own`; `role=employee` → only self |
| Cloud storage – “Anyone with the link can view” | ABAC + ReBAC | Google Drive – permission based on `resource.shareLink.enabled=true` and `request.user has link` |
| Healthcare (HIPAA) – a nurse can view a patient’s record only if assigned to that patient and during shift | ABAC with time & relationship | Condition: `user.assignedPatients.contains(patient.id) AND now() between user.shiftStart and user.shiftEnd` |
| Git repository – user can push to `main` only if they are a maintainer | ACL / ReBAC | GitHub – each repo has a list of maintainers, writers, readers |

---

### 3. Encryption at Rest

**How it works:** Data stored on disk (databases, files, backups, logs) is encrypted so that an attacker who steals physical drives cannot read the data.

**Types:**
- **Full‑disk encryption** (OS level, protects against physical theft)
- **Database transparent data encryption (TDE)** (database handles key management)
- **Application‑level encryption** (app encrypts before writing – most control)
- **Client‑side encryption** (user holds the key, cloud provider never sees plaintext)

**Scenario & Example:**

| Scenario | Technique | Example |
|----------|-----------|---------|
| Cloud database containing PII (credit cards, SSNs) | Database TDE + column‑level encryption | AWS RDS with TDE turned on; for credit card numbers, use application‑level encryption with KMS |
| Laptop stolen from employee | Full‑disk encryption (BitLocker / FileVault) | Corporate laptop – BitLocker with TPM; without the password, drive is unreadable |
| User storing sensitive documents on Dropbox | Client‑side encryption (user holds key) | Cryptomator – encrypts files locally before syncing to cloud |
| Backups stored on tape or off‑site | Server‑side encryption with customer‑managed key | AWS S3 Backup with SSE‑KMS (keys rotated every 90 days) |

---

### 4. Encryption in Transit (TLS)

**How it works:** All data sent over a network is encrypted using TLS (formerly SSL). Prevents eavesdropping, man‑in‑the‑middle attacks, and tampering.

**Scenario & Example:**

| Scenario | Implementation | Example |
|----------|----------------|---------|
| User browser to web server | TLS 1.3 with strong ciphers | Any HTTPS website – certificate from Let’s Encrypt, TLS 1.3 enforced |
| Microservice to microservice inside a VPC | mTLS (mutual TLS) | Istio or Linkerd – sidecar proxies automatically encrypt and authenticate all service‑to‑service traffic |
| Database client to database server | TLS‑encrypted connection | PostgreSQL with `ssl=require` – prevents sniffing of queries on the internal network |
| API calls to external payment gateway | TLS + certificate pinning (optional) | Stripe API – all endpoints only accept HTTPS; they pin their root CA in mobile SDKs |

**Key point:** Encrypting inside a “trusted” network is still necessary (zero trust principle). An attacker who compromises a switch or a hypervisor can sniff all traffic.

---

### 5. Network Segmentation & Firewalls

**How it works:** Divide the network into logical segments (VPCs, subnets, security groups) and control traffic flow between them. Minimizes blast radius.

**Scenario & Example:**

| Scenario | Technique | Example |
|----------|-----------|---------|
| Web application with database | Separate subnets + security group rules | AWS: public subnet for load balancer, private subnet for web servers, isolated subnet for DB. DB security group only allows port 3306 from web server security group |
| PCI‑compliant environment (credit card processing) | Network segmentation + web application firewall (WAF) | E‑commerce site: cardholder data environment (CDE) is isolated; only approved services can talk to it |
| Zero trust microservices | Service mesh with sidecar proxies and policy engine | Google BeyondCorp – no internal network trust; every request is authenticated and authorized |

### 6. Input Validation & Output Encoding (Preventing Injection)

**How it works:** Never trust user input. Validate on both client and server. Encode output based on context (HTML, SQL, JSON, shell). Prevents SQL injection, XSS, command injection, etc.

**Scenario & Example:**

| Attack | Defense | Example |
|--------|---------|---------|
| SQL injection – user enters `' OR '1'='1` as username | Parameterized queries / prepared statements | `SELECT * FROM users WHERE name = ?` – the `?` is bound, never interpreted as SQL code |
| Cross‑site scripting (XSS) – user posts `<script>alert('hack')</script>` in a comment | Output encoding (HTML entity encoding) | `&lt;script&gt;...` – browser displays as text, not executable |
| Command injection – user uploads file named `; rm -rf /` | Whitelist allowed characters + use safe APIs | Reject any filename containing `;`, `|`, `` ` ``, `$`; use `subprocess` with list of args (not shell=True) |
| LDAP injection | Input sanitization + allowlist | Only allow alphanumeric characters in search filters |

**Real‑world failure:** Equifax (2017) – an unpatched Apache Struts vulnerability allowed remote code execution via malicious HTTP parameters. 147 million records stolen.

### 7. Secrets Management

**How it works:** API keys, database passwords, certificates, and tokens are never hardcoded in source code. They are stored in a secure vault, rotated regularly, and injected at runtime.

**Scenario & Example:**

| Scenario | Tool / Method | Example |
|----------|---------------|---------|
| Application needs DB password | HashiCorp Vault / AWS Secrets Manager | Microservice retrieves `DB_PASSWORD` from Vault at startup; Vault audits every access |
| CI/CD pipeline needs cloud credentials | Short‑lived tokens (OIDC) instead of long‑lived keys | GitHub Actions → AWS – uses OIDC to get a temporary credential valid for 1 hour |
| Kubernetes pod needs API key | Kubernetes Secrets + external secrets operator | Secret is stored in AWS Secrets Manager; the operator syncs it into the pod as a mounted file |
| Rotation of database password without downtime | Vault dynamic secrets | Vault generates a temporary DB credential on each request; no password stored anywhere |

**Anti‑pattern:** Hardcoding `apiKey = "sk_live_abc123"` in GitHub. This is how many breaches start (e.g., Uber 2016).

---

### 8. Audit Logging & Monitoring

**How it works:** Record who did what, when, where, and from which IP. Logs must be tamper‑proof (write‑once, append‑only) and sent to a separate, immutable store.

**Scenario & Example:**

| Scenario | What to log | Example |
|----------|-------------|---------|
| Compliance (SOX, HIPAA, PCI) | All access to sensitive data (PII, PHI, credit cards) | Healthcare app logs every time a patient record is viewed: `user_id, patient_id, timestamp, action, IP` |
| Security incident detection | Failed login attempts, privilege escalations, unusual geo‑locations | AWS CloudTrail logs all API calls to S3; an alert triggers when a user deletes an S3 bucket |
| Forensics after a breach | Immutable logs sent to a separate account | Use AWS S3 Object Lock (WORM mode) or Google Cloud Logging with retention locks |
| Insider threat detection | Data exfiltration patterns (e.g., downloading 10,000 records at 3 AM) | SIEM (Splunk, Sentinel) correlates logs and triggers an alert |

---

### 9. Rate Limiting & Throttling (Availability Security)

**How it works:** Limit the number of requests a client can make in a given time window. Protects against DDoS, brute force attacks, and resource exhaustion.

**Scenario & Example:**

| Scenario | Algorithm | Example |
|----------|-----------|---------|
| Login endpoint – prevent password brute force | Fixed window counter | Max 5 attempts per minute per IP; after 10 failures, CAPTCHA required |
| API exposed to public – prevent abusive scraping | Token bucket or leaky bucket | Twitter API: 900 requests per 15 minutes per user token |
| Microservice – protect downstream database | Concurrency limit + queue | Each service instance allows max 10 concurrent DB connections; excess requests are queued or rejected |
| Global DDoS mitigation | Edge rate limiting (Cloudflare, AWS Shield) | Cloudflare rate limit: 100 requests per 10 seconds per IP; returns 429 Too Many Requests |

---

### 10. Web Application Firewall (WAF) & DDoS Protection

**How it works:** WAF inspects HTTP/HTTPS traffic and blocks common attacks (SQLi, XSS, path traversal). DDoS protection absorbs volumetric attacks.

**Scenario & Example:**

| Scenario | Tool | Example |
|----------|------|---------|
| E‑commerce site during Black Friday | Cloud‑based WAF (AWS WAF, Cloudflare, Akamai) | AWS WAF rule: block requests with `User-Agent` matching `sqlmap` or `curl` |
| Protecting against OWASP Top 10 | Managed rule sets | Cloudflare Managed Ruleset blocks Log4j exploits (`${jndi:...}`) in request headers |
| Large‑scale DDoS (UDP flood, SYN flood) | Anycast network + scrubbing centers | Cloudflare – traffic is routed to their global anycast network; malicious traffic is dropped at the edge |

**Real‑world:** GitHub survived a 1.35 Tbps DDoS attack in 2018 using Akamai’s Prolexic.

---

### 11. Identity & Access Management (IAM) for Infrastructure

**How it works:** Apply least privilege to human users and machine roles. No long‑term credentials. Use short‑lived, scoped permissions.

**Scenario & Example:**

| Scenario | Best Practice | Example |
|----------|---------------|---------|
| Developer needs to restart a service, but not delete production DB | Fine‑grained IAM policies | AWS IAM: `ec2:StartInstances` on specific resource tag `environment=prod` but not `rds:DeleteDBInstance` |
| CI/CD server needs to deploy code | Use OIDC or instance role – no hardcoded keys | GitHub Actions assume an IAM role via OIDC; the role has `s3:PutObject` only to the deployment bucket |
| Temporary contractors | Time‑bound permissions with expiration | Azure AD – guest user account expires after 30 days; permissions are automatically revoked |
| Service account for monitoring | Read‑only permissions, rotate every 90 days | Prometheus service account: `view` role in Kubernetes (can read metrics but not create pods) |

---

### 12. Data Masking & Tokenization

**How it works:** Replace sensitive data with a non‑sensitive placeholder (token) or mask it in logs/UIs. The original data is stored in a separate vault.

**Scenario & Example:**

| Scenario | Technique | Example |
|----------|-----------|---------|
| Customer service agent sees a credit card number | Tokenization + last‑4 only | Agent sees `•••• •••• •••• 1234`. Full card is in PCI vault; token `tok_abc123` references it |
| Logging user email addresses | Data masking (partial redaction) | Log shows `user@example.com` → `u***@e***.com` |
| Analytics on PII without exposing raw data | Pseudonymization (deterministic encryption) | Encrypt SSN with a key; analytics join on the ciphertext, never plaintext |
| Test environments need realistic but fake data | Synthetic data generation | Replace real names with `John Doe`, credit cards with `4111-1111-1111-1111` (test PAN) |

### 13. Security Headers (Defense in Depth for Web)

**How it works:** HTTP response headers that instruct the browser to enforce security policies.

| Header | What it does | Example |
|--------|--------------|---------|
| `Content-Security-Policy` | Prevents XSS by whitelisting script sources | `default-src 'self'; script-src 'self' https://trusted-cdn.com` |
| `Strict-Transport-Security` | Forces HTTPS only (HSTS) | `max-age=31536000; includeSubDomains; preload` |
| `X-Frame-Options` | Prevents clickjacking (your site in an iframe) | `DENY` or `SAMEORIGIN` |
| `X-Content-Type-Options` | Prevents MIME sniffing | `nosniff` |
| `Referrer-Policy` | Controls how much referrer info is sent | `strict-origin-when-cross-origin` |

**Scenario:** Banking website – sets CSP to only allow scripts from `bank.com` and Stripe’s JS. Any injected `<script src="evil.com">` will be blocked by the browser.

| Scenario | Primary Technique | Secondary |
|----------|------------------|-----------|
| User logs into a web app | Password + MFA (TOTP) | Rate limiting on login |
| A microservice calls another service | mTLS + OAuth2 JWT | Network segmentation (service mesh) |

| Logging user actions for compliance | Immutable audit logs (WORM) + real‑time alerting | Logs sent to separate SIEM account |

| Large‑scale DDoS attack | Anycast CDN + rate limiting at edge | Auto‑scaling (absorb traffic) + failover |
| Developer needs access to production | Just‑in‑time (JIT) access with approval (e.g., Teleport) | Session recording + expiration after 4 hours |
| Third‑party vendor needs API access | OAuth2 client credentials grant + IP whitelist | Short‑lived tokens (1 hour) |

## Common Anti‑patterns for Security

1. **Rolling your own crypto** – Never invent your own encryption or hashing. Use well‑vetted libraries (libsodium, Tink, AWS KMS).
2. **Hardcoding secrets** – Secrets in source code, config files, or environment variables (use a secrets manager).
3. **Trusting the network** – “Internal network is safe” is obsolete. Implement zero trust.
4. **Lack of input validation** – Trusting user input leads to injection attacks.
5. **Over‑permissive IAM** – Giving `*:*` or “admin” to everything. Follow least privilege.
6. **Not logging security events** – Without logs, you can’t detect or investigate a breach.
7. **No MFA** – Passwords alone are not enough. MFA stops 99.9% of account takeovers (Microsoft).
8. **Using outdated TLS versions** – TLS 1.0 and 1.1 are broken. Use TLS 1.2 or 1.3.
9. **Storing passwords in plaintext or weak hashes** – Use bcrypt, scrypt, Argon2 (not MD5, SHA1).
10. **Disabled security headers** – Missing CSP or HSTS exposes your users to XSS and protocol downgrade.

## Summary for HLD Interviews – Security

> *“To ensure security in the HLD, I follow defense in depth: at the network layer, I segment VPCs and enforce mTLS for service‑to‑service communication. At the application layer, I implement strong authentication (MFA, OAuth2) and fine‑grained authorization (RBAC/ABAC). All data is encrypted at rest using KMS and in transit with TLS 1.3. I use parameterized queries to prevent SQL injection and output encoding to prevent XSS. Secrets are stored in a vault (e.g., HashiCorp Vault) and rotated regularly. I enable audit logging with immutable storage and set up rate limiting and a WAF to mitigate DDoS and brute force attacks. Finally, I apply the principle of least privilege to all IAM roles and regularly test the design against the OWASP Top 10.”*
