This is a polished practice guide designed to help you navigate a real-world System Design interview. In this environment, the "Problem Statement" is usually just one sentence: **"Design a URL shortening service like Bitly."**

Everything else—the constraints, the numbers, and the specific features—must be "extracted" by you through strategic clarifying questions.

---

## The Interviewer’s Script
Use this script to simulate the conversation flow and see if you can arrive at a high-level design by asking the right questions.

### Phase 1: Functional Requirements
**You ask:** *"What are the core features? Do we need user accounts? Custom aliases?"*

**Interviewer's Answers:**
* **Core:** The system must take a long URL and return a short link. When that link is clicked, it must redirect to the original.
* **Customization:** Users should be able to pick their own short link (e.g., `bit.ly/my-promo`) if it's available.
* **Deletion/Expiration:** For now, links don't expire automatically, but we might want a TTL (Time-to-Live) feature later.
* **Analytics:** Yes, we need to track how many times a link was clicked.
* **Scope:** Focus on the public API first. Don't worry about a UI/Frontend for now.

---

### Phase 2: Non-Functional Requirements
**You ask:** *"What is the scale? Is availability more important than consistency? What is the target latency?"*

**Interviewer's Answers:**
* **Scale:** We are looking at a global scale (millions of users).
* **Latency:** Redirection must be "instant." A user shouldn't notice the delay.
* **Availability:** High availability is a priority. If the service is down, millions of links across the internet "break."
* **Consistency:** For custom aliases, we need strong consistency (two people shouldn't claim the same name). For standard redirects, eventual consistency is fine.

---

### Phase 3: Traffic Estimation & Capacity Planning
**You ask:** *"How many new URLs are created daily? What is the read/write ratio?"*

**Interviewer's Answers:**
* **Writes:** Let's assume **100 million** new URLs are created per month.
* **Reads:** This is a read-heavy system. Assume a **100:1 read-to-write ratio**.
* **Retention:** We want to store these mappings for **5 years**.
* **URL Length:** Assume a long URL is about 200 characters on average.

---

### Phase 4: API Design
**You ask:** *"Should it be RESTful? Do we need to handle bulk shortening?"*

**Interviewer's Answers:**
* Keep it simple: A standard REST API is fine.
* We don't need bulk shortening for the MVP.
* Include a way to get analytics for a specific short code.

---

### Phase 5: Database Design
**You ask:** *"Do we need complex relationships or joins? Is the data model expected to change?"*

**Interviewer's Answers:**
* The data is very simple: **Short Code -> Long URL**.
* We don't have complex relations between links.
* The most common query is a simple lookup by the short code ID.

---

### Phase 6: Detailed Component Design (The "Deep Dives")
The interviewer will push you here with specific "What if" scenarios:
* **ID Generation:** *"How will you ensure two different application servers don't generate the same short code at the exact same time?"*
* **The "KGS":** *"If you use a database to generate IDs, isn't that a single point of failure and a bottleneck? How do you fix that?"*
* **Viral Links:** *"What happens if a celebrity tweets a link and 1 million people click it in 1 minute? How does your system handle that 'Hot Key' problem?"*
* **The Redirect Type:** *"Should we use HTTP 301 or 302? What are the pros and cons for our analytics?"*
* **Invalid Links:** *"What if someone writes a script to guess random short codes that don't exist? How do you prevent those requests from hitting your database every time?"*

---

### Phase 7: Multi-Region & Failures
**You ask:** *"Is this for a single region or global?"*

**Interviewer's Answers:**
* The users are global. A user in Tokyo shouldn't have to wait for a server in Virginia to redirect them.
* What happens if an entire AWS Region goes offline? How does your design stay alive?

## Mapping Context to Interviewer Inputs
This section ensures you know exactly which detail from your study notes corresponds to the interviewer's prompts.

### 1. Requirements & Scope
* **Your Knowledge:** Core (Shorten/Redirect), Optional (Custom Alias, Expiration, Analytics).
* **Interviewer's Prompt:** They will confirm these features but often ask you to **prioritize**. Focus on the redirect and shortening first; handle analytics as a background process.

### 2. The Numbers (Traffic & Storage)
* **Your Knowledge:** 100M URLs/month, 100:1 Read/Write, ~10TB storage over 5 years.
* **Interviewer's Prompt:** They provide the "100M/month" and "100:1" anchors. They expect **you** to do the math to reach the storage (~10TB) and QPS (~4k average reads/sec) figures.
* **Tip:** If you forget the math, the interviewer will prompt: *"Given 100M writes a month, how much disk space do we need for 5 years?"*

### 3. ID Generation (The "Senior" Section)
* **Your Knowledge:** KGS (Key Generation Service), Snowflake IDs, Base62 encoding.
* **Interviewer's Prompt:** This is where the interviewer will "poke" your design. They will ask: *"How do we ensure two servers don't pick the same ID?"* or *"If we use a database for IDs, how do we handle the bottleneck?"*

### 4. Database & Caching
* **Your Knowledge:** NoSQL (DynamoDB/Cassandra), Redis LRU, Cache-aside.
* **Interviewer's Prompt:** They will ask: *"Why NoSQL over SQL?"* or *"What happens if the cache is full?"*

### 5. Advanced Resilience
* **Your Knowledge:** Bloom Filters, 301 vs 302, CDN for viral links.
* **Interviewer's Prompt:**
    * **The "Spam" Trap:** *"What if someone hits us with millions of random, non-existent short codes?"*
    * **The "Viral" Trap:** *"A celebrity just shared a link. How do we keep the DB from crashing?"*
    * **The "Analytics" Trap:** *"If we use 301 redirects, will we still see every click in our analytics?"*

---

## Summary Practice Checklist
To ensure you've "checked all the boxes," make sure you can explain these **5 Key Technical Nuances**:

1.  **Bloom Filters:** Explain how they sit in front of the cache to protect the database from "404 spam."
    
2.  **KGS Batching:** Explain that servers take 1,000 IDs at a time to stay stateless and fast.
3.  **Active-Active Replication:** Explain how we use DynamoDB Global Tables or Cassandra so a user in London isn't waiting on a server in New York.
4.  **Async Analytics:** Explain the use of Kafka so the user gets their redirect immediately while the "logging" happens in the background.
5.  **Base62 Math:** Be ready to show that 7 characters cover trillions of URLs ($62^7 \approx 3.5 \text{ Trillion}$).
