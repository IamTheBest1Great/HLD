# Pastebin System Design — Mock Interview Practice Guide

**The Problem Statement (what the interviewer says):**
> *"Design a text sharing service like Pastebin."*

Everything else — the scale, the features, the constraints — must be extracted by you through smart clarifying questions.

---

## The Interviewer's Script

### Phase 1: Functional Requirements
**You ask:** *"What are the core features? Do users need accounts? Can pastes be private?"*

**Interviewer's Answers:**
- **Core:** Users paste text and get back a short URL. Anyone with that URL can read the content.
- **Content types:** Plain text only for MVP. Optionally support a language hint for syntax highlighting (rendered client-side).
- **Expiration:** Pastes can have a TTL — 10 minutes, 1 hour, 1 day, 1 month, or never. The system must auto-delete expired pastes.
- **Visibility:** Pastes are public by default. Unlisted (link-only) is a bonus. Private (auth required) is optional.
- **User accounts:** Optional. Users can log in to manage and delete their pastes.
- **Analytics:** Track view counts per paste. Detailed geo/device stats are a bonus.
- **Scope:** Focus on the core create and read flows first. Ignore the frontend.

---

### Phase 2: Non-Functional Requirements
**You ask:** *"What scale are we designing for? Is availability more important than consistency? What's the acceptable latency?"*

**Interviewer's Answers:**
- **Scale:** Global. Millions of users across continents.
- **Latency:** Reading a paste must feel instant — under 100ms. Creating a paste can be up to 500ms.
- **Availability:** Very high. If the service is down, shared links across the internet break. 99.99% target.
- **Consistency:** Strong consistency for custom aliases (two users cannot claim the same alias). Eventual consistency is fine for reads — a new paste can take a second to appear globally.
- **Durability:** Paste content must never be lost once created. Replication and backups are mandatory.

---

### Phase 3: Traffic Estimation & Capacity Planning
**You ask:** *"How many new pastes are created daily? What's the read-to-write ratio? What's the average paste size?"*

**Interviewer's Answers:**
- **Writes:** Assume **1 million new pastes per day**.
- **Reads:** This is a read-heavy system. Assume a **100:1 read-to-write ratio** — 100 million reads per day.
- **Paste size:** Average paste is **10 KB**. Maximum allowed is **10 MB**.
- **Retention:** Permanent pastes should survive for at least **5 years**.

**What the interviewer expects YOU to calculate:**

| Metric | Your Calculation |
|--------|-----------------|
| Writes/sec (avg) | 1M / 86,400 ≈ **11.6 writes/sec** |
| Peak writes (3×) | ≈ **35 writes/sec** |
| Reads/sec (avg) | 100M / 86,400 ≈ **1,157 reads/sec** |
| Peak reads (3×) | ≈ **3,470 reads/sec** |
| Daily storage (content) | 1M × 10 KB = **10 GB/day** |
| 5-year storage (with 3× replication) | 10 GB × 365 × 5 × 3 = **54.75 TB** |
| Daily egress bandwidth | 1,157 reads/sec × 10 KB = **~11.5 MB/sec** |

---

### Phase 4: API Design
**You ask:** *"Should it be RESTful? Do we need bulk paste creation? How does content get delivered — streamed or downloaded?"*

**Interviewer's Answers:**
- Standard REST API is fine.
- No bulk creation for MVP.
- Content is returned in the response body as plain text.
- Include an endpoint to fetch analytics for a paste (auth-gated).

**The 3 endpoints you must define:**

```
POST   /v1/pastes                        → Create paste, return paste_key + URL
GET    /v1/pastes/{pasteKey}             → Return content + metadata
GET    /v1/pastes/{pasteKey}/analytics   → Return view stats (auth required)
```

**The interviewer will push:** *"What HTTP status code do you return for an expired paste — 404 or something else?"*
> Correct answer: **410 Gone** — signals "this existed but no longer does," unlike 404 which means "never existed."

---

### Phase 5: Database Design
**You ask:** *"How large is the content? Should content live in the database or elsewhere? Do we need complex queries?"*

**Interviewer's Answers:**
- Content can be up to 10 MB — way too large for a database row.
- The most common query is a simple lookup by paste key.
- We need to list all pastes for a given user (secondary access pattern).
- Expiration should be automatic — we don't want a cron job manually cleaning rows.

**What the interviewer expects you to say:**

The fundamental Pastebin insight — store **content in object storage (S3)**, store **metadata in NoSQL (DynamoDB)**. The metadata row holds a pointer (S3 object key) to the actual content.

**The interviewer will push:** *"Why not store the text directly in DynamoDB?"*
> Correct answer: DynamoDB rows have a 400 KB item size limit. Even without that limit, storing large blobs in a database bloats storage costs, destroys index performance, and saturates DB memory. S3 is purpose-built for cheap, durable, scalable blob storage.

### Phase 6: Detailed Component Design — The "Deep Dives"

The interviewer will poke your design with specific "What if" scenarios:

**ID Generation:**
> *"How do you ensure two app servers don't generate the same paste key simultaneously?"*

Expected answer: Key Generation Service (KGS) — a dedicated service that pre-generates Base62 keys in batches. Each server claims a batch of 500 keys atomically (using a conditional write or distributed lock). Keys within that batch are exclusively owned by that server, so no collision is possible.

**The Atomicity Problem:**
> *"What if the S3 upload succeeds but the DynamoDB write fails? You now have an orphaned file in S3 with no metadata pointing to it. How do you handle this?"*

Expected answer: A nightly cleanup job scans S3 for objects with no matching metadata row older than 24 hours and deletes them. The 24-hour grace period prevents race conditions where a new paste's metadata simply hasn't replicated yet.

**Expiration — Three Layers:**
> *"How do you make sure expired pastes are actually cleaned up? What if your cleanup worker crashes?"*

Expected answer: Three independent safety nets — DynamoDB TTL auto-deletes metadata rows at `expires_at`. Redis TTL ensures no stale cached data is served. S3 Lifecycle Policies delete objects with an expiry tag after N days. The cleanup worker is a fourth layer consuming DynamoDB Streams, but the system degrades gracefully without it.

**Private Pastes and CDN:**
> *"You said CDN caches paste content for speed. But what if the paste is private? Now the CDN is serving protected content to anyone who has the URL."*

Expected answer: Private pastes set `Cache-Control: private, no-store` headers. CDN never caches them. The app server validates the auth token first, then streams the content directly from S3 — the pre-signed URL is never given to the client.

**Viral / Hot Paste:**
> *"A developer shares a paste on Hacker News and 500,000 people open it in 10 minutes. How does your system not collapse?"*

Expected answer: CDN (CloudFront) caches the content response at edge nodes globally. The first request to each edge populates the cache; every subsequent request from that region is served from the edge — zero load on app servers or S3 origin. The app server's only role is issuing the first cache-miss response.

**Content Scanning:**
> *"What if someone pastes 10,000 lines of stolen credit card numbers? Or malware scripts? How do you detect and prevent abuse?"*

Expected answer: Async content scanning pipeline — paste is accepted and stored, then a background worker runs heuristics (PII patterns, known malware signatures, CSAM hash matching). Flagged pastes are soft-deleted and queued for human review. Synchronous scanning on the write path would add unacceptable latency.

**The 410 vs 404 Edge Case:**
> *"A user bookmarked a paste that expired yesterday. They open the bookmark today. What does your system return, and how does it know the difference between 'never existed' and 'existed but expired'?"*

Expected answer: DynamoDB TTL deletes the row, but you can use soft deletes — mark rows as `status: expired` rather than hard deleting immediately. On read, if `status = expired` → return 410 Gone. If row doesn't exist at all → return 404 Not Found. After 30 days, a cleanup job hard-deletes the soft-deleted rows.

### Phase 7: Multi-Region & Failures
**You ask:** *"Are users global? What's the acceptable data loss in a regional outage?"*

**Interviewer's Answers:**
- Users are worldwide. A user in Singapore shouldn't wait on a server in Virginia.
- RPO (Recovery Point Objective): near zero — no paste should be lost in a regional failure.
- RTO (Recovery Time Objective): under 60 seconds — failover must be automatic.

**What the interviewer expects:**
- **DynamoDB Global Tables**: active-active replication across regions. Writes accepted anywhere, replicated globally within seconds.
- **S3 Cross-Region Replication (CRR)**: paste content replicated to all regions automatically.
- **Route53 GeoDNS + health checks**: routes users to nearest region; fails over automatically if a region's health check fails.
- **Redis per region**: each region has its own Redis cluster seeded from local DB — no cross-region cache dependency.

## Mapping Context to Interviewer Inputs

### 1. The Fundamental Insight
- **Your knowledge:** Content in S3, metadata in NoSQL, CDN for reads.
- **Interviewer's prompt:** *"Why not just store everything in one database?"*
- **Your answer must cover:** The 10 MB blob size problem, DB performance degradation, and why S3 is purpose-built for this.

### 2. The Numbers
- **Your knowledge:** 1M pastes/day, 100:1 read:write, 10 KB average.
- **Interviewer's prompt:** *"Given those write numbers, how much storage do we need over 5 years?"*
- **Your answer must cover:** 54.75 TB calculation, replication factor of 3×, compression as optimization (gzip reduces text 60-80%, so effective storage ~11-22 TB).

### 3. The Expiry System
- **Your knowledge:** Three-layer TTL (Redis + DynamoDB + S3 Lifecycle).
- **Interviewer's prompt:** *"Your cleanup worker crashes. What happens to expired pastes?"*
- **Your answer must cover:** DynamoDB TTL and S3 Lifecycle are independent of the cleanup worker — the system self-heals.

### 4. The CDN / Private Paste Tension
- **Your knowledge:** CDN for public pastes, proxied reads for private.
- **Interviewer's prompt:** *"You can't use the same CDN strategy for private and public pastes. How do you differentiate?"*
- **Your answer must cover:** `Cache-Control` headers, auth validation before S3 access, never returning pre-signed URLs to unauthenticated clients.

### 5. The Write Atomicity Problem
- **Your knowledge:** S3 upload + DynamoDB write are two separate operations.
- **Interviewer's prompt:** *"These two writes are not atomic. How do you handle partial failure?"*
- **Your answer must cover:** Write S3 first (idempotent, safe to retry), then DynamoDB. Cleanup job handles orphaned S3 objects.

## Key Differences from URL Shortener (What Interviewers Specifically Test)

Interviewers who give you Pastebin after URL Shortener are testing whether you recognize these distinct challenges:

| Challenge | URL Shortener | Pastebin — What Changes |
|-----------|---------------|------------------------|
| Payload size | 200 bytes | Up to 10 MB — changes everything |
| Primary storage | NoSQL only | S3 + NoSQL (split architecture) |
| CDN role | Optional | Critical and mandatory |
| Response type | HTTP redirect | Full content delivery |
| Expiry complexity | Simple TTL row deletion | Three-layer TTL + S3 Lifecycle + cleanup worker |
| Content safety | URL validation only | PII detection, malware scan, CSAM hashing |
| Bandwidth cost | Negligible | ~1 TB/day — a real cost concern |
| 404 vs 410 | Not relevant | Core part of the API contract |

---

## Summary Practice Checklist

Before your interview, make sure you can explain these **6 Key Technical Nuances** without notes:

1. **S3 + Metadata Split**: Why blobs go to S3 and metadata goes to NoSQL. Be ready to explain what breaks if you store blobs in DynamoDB rows.

2. **Three-Layer Expiry**: Redis TTL + DynamoDB TTL + S3 Lifecycle Policy. Know what each layer protects against and what happens if any one of them fails.

3. **CDN Cache Invalidation for Public vs Private**: `Cache-Control: public` for public pastes, `Cache-Control: private, no-store` for private ones. Know why you can't use pre-signed S3 URLs for private content.

4. **Write Atomicity (S3 → DynamoDB)**: Two non-atomic writes. Write S3 first, then DB. Orphan cleanup via nightly job. Know the 24-hour grace window and why it exists.

5. **410 Gone vs 404 Not Found**: Soft-delete expired rows instead of hard-deleting. Return 410 for expired, 404 for never-existed. Hard delete after 30-day grace window.

6. **Compression as Cost Optimization**: Text compresses 60-80% with gzip. 54 TB of raw storage becomes 11-22 TB effective. This is the answer when the interviewer asks *"How do you reduce storage costs at scale?"*
